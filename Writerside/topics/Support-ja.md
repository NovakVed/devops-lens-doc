# サポート

%product% に関する要望や不具合は、すべて公開リポジトリ
[%tracker_url%](%tracker_url%) で管理しています。ソースコードは置かれておらず、issue テンプレートと Discussions
だけのリポジトリです。プラグイン本体のリポジトリは非公開の ままでも、誰でも公開の場で問題を報告できるようにするためのものです。

## 窓口の使い分け

| こんなとき                                                           | どこへ                                                                                                          |
|----------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| 「IDE に赤いエラーアイコン／このプラグインのエラーダイアログが出た」 | そのダイアログの **Report to the Third-Party Plugin** を押してください。[クラッシュレポート](#crash-reports)を参照 |
| 「壊れていて、再現もできる」                                         | [バグを報告](%new_bug_url%)                                                                                     |
| 「こんなことができるようになってほしい」                             | [機能をリクエスト](%new_feature_url%)                                                                           |
| 「これはどう使うの？」「この挙動で合っている？」                     | [Discussions](%discussions_url%)                                                                                |
| 「セキュリティ上の問題を見つけたかもしれない」                       | [%support_email%](mailto:%support_email%) にメール。**公開 issue には書かないでください**                       |
| 「ドキュメントが間違っている・足りない」                             | [トラッカー](%issues_url%)に登録してください。こちらで振り分けます                                              |
| Azure DevOps 自体の不具合                                            | [Microsoft Developer Community](https://developercommunity.visualstudio.com/AzureDevOps)                        |
| プラグインとは無関係な IDE の不具合                                  | [JetBrains YouTrack](https://youtrack.jetbrains.com/issues)                                                     |

質問は Discussions で歓迎しています。「バグではないから」という理由でクローズすることは ありません。議論の結果、実際の不具合だと分かった場合は
issue に変換されます。

## クラッシュレポート {id="crash-reports"}

プラグインが予期しないエラーをスローすると、IDE は標準のエラーダイアログを表示し、そこに **Report to the Third-Party Plugin**
ボタンが現れます。このボタンは、押す価値がもっとも高いものです。`idea.log` を探して読まなくても、バグを実際に特定できる部分であるスタックトレースが送られます。

そのレポートを組み立てて送信するのは IDE で、JetBrains Marketplace
を経由してプラグイン開発者に届きます。公開リポジトリに送られることはありません。可能であれば、何をしていたかをダイアログのコメント欄に一文書き添えてください。スタックトレースと「コンフリクトのある
PR で Approve を押した」の一文があれば、たいていは修正できます。入力した内容はそのまま送信され、プラグインはレポートを取捨選択できないため、コード、資格情報、機密性のある名称は書かないでください。

クラッシュレポートには返信先がないため、返信できません。 **回答がほしい場合は issue も登録してください。** 両者は互いを補い合います。

レポートに何が含まれるか、そしてクラッシュレポートを一切送らずにバグを報告する方法の
詳細は[プライバシーとデータ](Privacy-and-Data-ja.md#crash-reports)にあります。

## バグを報告する

いちばん速いのは IDE から始める方法です。報告者が書き漏らしがちな項目が自動で 埋まります。

<procedure title="IDE から報告する" id="report-from-ide">
    <step><ui-path>Help | Report DevOps Lens Issue…</ui-path> を選択します。または
        <ui-path>Settings | Tools | DevOps Lens</ui-path> を開き、ページ下部の
        <b>Report a bug</b> をクリックします。</step>
    <step>ブラウザーでバグ報告フォームが開き、IDE のビルド、プラグインのバージョン、OS
        が入力済みの状態になります。送信されるのはこれだけで、提出前に自由に編集・削除
        できます。</step>
    <step>残りの環境情報については、<ui-path>Help | Copy DevOps Lens
        Diagnostics</ui-path> を実行し、スナップショットを確認してから issue に
        貼り付けてください。</step>
</procedure>

設定画面のリンクは <b>AI Settings</b> のサブページ下部にもあります。もちろん
[トラッカー](%issues_url%)を直接開いてもかまいません。

### 報告する前に

<procedure id="before-you-file-steps">
    <step><a href="%issues_url%?q=is%3Aissue">オープン・クローズ両方の issue を検索</a>
        してください。すでに登録済みかもしれません。その場合は重複を作るより既存の issue
        にコメントするほうが有益です。</step>
    <step><a href="Troubleshooting-ja.md"/>に目を通してください。
        プルリクエスト一覧が空になる、401 / 403 エラー、OAuth のリダイレクトが IDE に
        戻らない、インラインコメントが表示されない — いずれも既知の対処法があります。</step>
    <step>プラグインを最新バージョンに更新し（<ui-path>Settings | Plugins |
        Updates</ui-path>）、それでも再現するか確認してください。</step>
</procedure>

### フォームで聞かれること

以下が欠けている報告は、たいてい着手前に一往復のやり取りが必要になります。

- **プラグインのバージョン**と **IDE 名 + ビルド番号** — <ui-path>Help | About</ui-path> から
- **OS**
- **Azure DevOps の種別** — Services（クラウド、`dev.azure.com`）か Server（オンプレミス）か
- **サインイン方法** — PAT か Microsoft Entra ID か
- **正確な再現手順**と、期待していた動作
- **ログの抜粋** — [デバッグログを有効にする](Troubleshooting-ja.md#enabling-debug-logs)
  を参照し、再現させてから `idea.log` を採取してください
- 目で見て分かる問題なら **スクリーンショット**

> **公開 issue に PAT や OAuth リフレッシュトークンを絶対に貼り付けないでください。**
> プラグインは自身のログ出力にトークンを残しませんが、スクリーンショットや HTTP
> トレース、`git remote -v` の出力からは漏れることがあります。投稿前に必ず確認し、万一
> トークンが流出した場合は Azure DevOps で直ちに失効させてください。
>
> 非公開リポジトリ名、社内サーバーの URL、同僚のメールアドレスについても同様です。
> 再現に必要になることはほとんどありません。
> {style="warning"}

## 機能をリクエストする

良いリクエストは、解決策ではなく「困っていること」から始まります。そのほうが、お互いが
思いつかなかったより良い答えにたどり着く余地が残ります。[機能リクエストフォーム](%new_feature_url%)
では、今どうしているか、どこがつらいか、代わりに何を試したかを尋ねます。

機能リクエストと呼べるか迷う段階なら、まず [Discussions](%discussions_url%) で相談して ください。そこから形にしていけます。

## セキュリティに関する報告

脆弱性は公開 issue ではなく、件名に `[SECURITY]` を付けて
[%support_email%](mailto:%support_email%) までメールでご連絡ください。対象範囲を含む 方針の全文は、トラッカー上の
[SECURITY.md](%tracker_url%/blob/main/SECURITY.md) にあります。

対象となるのは、認証情報が漏れる可能性のあるもの、コードやリポジトリのデータが本来 送られるべきでない場所に送られるもの、そして細工された
Azure DevOps のレスポンス （プルリクエストのタイトル、コメント本文、パイプラインのログ）がコードを実行したり
ファイルシステムに到達したりするものです。設計上どのデータがどこへ送られるかは
[](Privacy-and-Data-ja.md)を参照してください。

## 対応の目安

%product% は 1 人で開発・保守しています。そのためトリアージは随時ではなくまとめて行われ、 おおむね 1
週間以内です。ログ付きで再現手順が明確な報告は、そうでないものより必ず速く 進みます。再現できない報告には質問を返し、返信がないままであればクローズします。機能
リクエストのクローズはアイデアの否定ではなく、現時点のスコープに入らないという意味です。
