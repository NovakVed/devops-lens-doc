# Screenshot capture guide

This is the shot list for the documentation site. Every image a topic references exists in [`images/`](images/) -
either a real capture or a **labeled placeholder PNG** - so the site always builds green. Images are organized into **feature-area
subfolders** (`getting-started/`, `pull-requests/`, `code-review/`, `comments/`, `pipelines/`, `ai/`, `git/`,
`notifications/`, `statistics/`, `settings/`) - the file paths below include the subfolder. To add a real screenshot,
**capture it and overwrite the placeholder at the same path** - no topic edits needed, the image just appears.

> **Topics reference images by bare filename, never by subfolder path.** Writerside scans `images/` recursively and
> resolves refs on filename alone: `![…](pr-tool-window.png)`, not `![…](pull-requests/pr-tool-window.png)`. A
> subfolder path silently resolves to nothing - the build still passes, but the page ships with no image. Because of
> that, **filenames must stay unique across all subfolders.**

## How to capture (keep them consistent)

- **Theme:** IntelliJ **New UI, Dark** (matches the placeholders and the doc site).
- **Crop tight:** capture just the relevant panel/dialog, not the whole screen. On macOS use <kbd>⌘⇧4</kbd> then <kbd>
  Space</kbd> to grab a single window, or drag to select a region.
- **Scale:** capture on a HiDPI/Retina display if you can - the images render up to the widths below, so 2× pixels stay
  crisp.
- **Data hygiene:** use a demo org/repo or scrub anything sensitive. Avoid real tokens, private repo names, or personal
  email addresses in frame.
- **Format:** PNG, same filename as the placeholder.

After dropping files in, run a build (push to `main`, or preview with the Writerside plugin) to see them live. Delete
this file before publishing if you prefer it not to ship - it lives outside `topics/` so it is **not** part of the built
site either way.

## Capture helper

`scripts/capture-screenshot.sh` writes a capture straight onto the image it replaces, so you never have to find
and rename files:

```bash
# 6-second delay: run it, switch to the IDE, set up the shot
scripts/capture-screenshot.sh pr-tool-window 6

# a localized shot -> images/pull-requests/pr-tool-window-ja.png
scripts/capture-screenshot.sh pr-tool-window 6 ja
```

It finds the sandbox IDE's window id (`scripts/window-id.swift`) and captures **by window** rather than by screen
region, which is what produces the transparent rounded corners the whole set has - a region capture bakes in whatever
is behind them. The 2x grab is then downsampled to the 1400px width the rest of the images use.

Set the sandbox window to the right size once per session, or the aspect will not match the existing shots:

```bash
osascript -e 'tell application "System Events" to tell process "java" to set size of window 1 to {1400, 838}'
```

If the capture comes back empty - Screen Recording permission denied, or the target window is on another Space - it
refuses to write rather than clobbering a good image with a black box.

> Capture and window control are **separate** macOS permissions. Capturing needs
> *Screen Recording*; driving the IDE (clicking, focusing a window) needs
> *Accessibility*, under <ui-path>System Settings | Privacy &amp; Security</ui-path>.
> This script only needs the first, because you set the shot up by hand.
> {style="note"}

## Localized screenshots (ja / ko / zh)

Localized topics reference a language-suffixed filename - `pull-requests/pr-tool-window-ja.png` beside `pull-requests/pr-tool-window.png` - so a
language gets its own image only once one has actually been captured; until then the topic keeps pointing at the shared
English file.

A localized shot needs **both halves** in the same language, or the frame comes out mixed:

| Half            | What it controls                                     | How to set it                                                                                    |
|-----------------|------------------------------------------------------|--------------------------------------------------------------------------------------------------|
| Plugin + IDE UI | tool window, chips, menus, dialogs                   | `azure/test-env/locale-packs/` - install the stubs, then `set-sandbox-locale.sh <config-dir> ja` |
| Seed content    | author names, PR titles, review comments, work items | `azure/test-env/onprem-mock/` - `MOCK_LOCALE=ja docker compose up -d`                            |

Restart the sandbox IDE after changing `MOCK_LOCALE`: the plugin caches the pull-request list in memory, so a plain
refresh keeps showing the previously fetched English content.

See `azure/test-env/locale-packs/README.md` for the full procedure and for why a JetBrains Language Pack cannot be used
(they stop at build 242).

> **Not yet fully localizable.** `AzureBundle` covers 484 strings, but much of the PR detail header, the reviewers
> sidebar, the comment composer and the Create-PR / Complete-PR / Run-Pipeline dialogs is still built from Kotlin string
> literals and renders in English whatever the locale. Capture localized shots of the tool window, filters, statistics
> and settings now; the deeper surfaces need those literals moved into the bundle first.
> {style="warning"}

Confirmed to localize cleanly (captured in all three on 2026-08-02): the **branch-widget popup**, the **attention-chip
tooltip**, the **in-editor review thread** (including its Resolve / Reply chrome), the **Suggested change** card, and the
**Summary settings** popup. Added 2026-08-03: the **Create Pull Request toolbar button and its tooltip**
(`pullRequests.toolwindow.createPr`) - the tool-window header, the filter chips and the seeded PR rows all translate, so
`create-pr-button-<lang>.png` is a fully localized frame.

> **AI output stays English.** The summary card's *chrome* localizes, but its body is model-generated and the prompt
> templates in `AzureAiPromptTemplates.kt` carry no "answer in the IDE language" instruction - so `ai/ai-summary-card-ja.png`
> and friends show Japanese/Korean/Chinese framing around English prose. That is what a user sees today; if the prompts
> gain a locale hint, re-shoot those three.
